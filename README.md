# 把旧版 PC QQ 的聊天记录补进 QQNT，再迁到 Mac 和手机：一次完整的核对、补写与迁移记录

这份文档记录了一次真实的 QQ 聊天记录迁移，分三段：

1. **补全**：旧版 PC QQ（`Msg3.0.db`）里的历史消息，QQNT 自带的导入器只导入了一部分。我们在数据库副本上逐条核对、补写、换库，再在客户端里验收。
2. **迁到 Mac**：把补全后的 Windows 记录搬到 Mac 上的 QQ，对比两边差异，补齐缺的消息和媒体。
3. **导到手机**：用 QQ 自带的「导出到手机」，把电脑上的完整记录传到 iPhone。

文档写了为什么要做、遇到了什么问题、怎么做的、哪些成功了、踩了哪些坑。

## 1. 结论先说

- **QQNT 自带的导入器不会把旧记录全部导进来。** 主账号旧版里有 524,471 条私聊和群聊记录，导入器只导入了约 10.6 万条。漏掉的主要是：带引用的回复、旧版经典表情、退出了的群、没有消息序号的群消息，以及撤回、通话等本地提示。
- **可以在数据库副本上补写，再整体替换回去。** 前提是每一种消息都先找到 QQNT 自己写的样本，按样本逐字节核对写法。每次换库前都先演练，并保留回滚源。
- **补写的内容，官方的备份和迁移都能带走。** 灰条、商城表情、回复、退出群的消息，通过电脑之间的备份导入、电脑导出到手机，都完整带过去了。
- **官方的备份和导出，私聊只带最近的 200 个。** 按最后一条消息的时间，从新到旧取，群不受这个限制。私聊多的账号，要分批导。
- **导出到手机一直卡住，很可能是手机 QQ 没有「本地网络」权限。** 我们为此查了 Tailscale、热点、IPv6，最后发现只是这个开关没打开。
- **图片和文件要单独处理。** 消息写进去以后，图片要放到 QQNT 认的位置，文件的旧路径要改。只看文件名或大小不能证明是原件，要用消息里记录的 md5 核对。
- **从手机再导回电脑，会把删掉的会话带回来，也会产生重复消息。** 导回之后要按会话和消息再清理一次。
- 最容易出错的不是写入本身，而是**判断哪些消息还缺**。必须逐条一对一核对，而不是看文件大小或界面上的数字。

## 2. 初衷

一台 Windows 电脑上有两个 QQ 账号，都从旧版 PC QQ 升级到了 QQNT。还有一台 MacBook Air 和一部 iPhone。要求是：

1. **旧聊天记录要在 QQNT 里看得到**：文字、图片、表情、回复，尽量和原来一样。
2. **不能破坏现有数据**：QQNT 里已有的消息一条都不能改。
3. **不要的直接删掉**：不再关心的群和聊天，从 QQNT 和旧数据里一起删除。
4. **电脑、Mac、手机都要有完整记录**。
5. **最后清理**：确认记录都进了 QQNT 之后，删掉旧版数据和中间文件，只保留移动硬盘上的一份原始备份。

## 3. 遇到的问题

| 问题 | 为什么麻烦 |
| --- | --- |
| 两种数据库都加密 | 旧版 `Msg3.0.db` 和 QQNT 的 `nt_msg.db` 用不同的加密方式，都需要密钥；Windows 和 Mac 上同一个账号的密钥也不同 |
| QQNT 的库有私有文件头 | `nt_msg.db` 前面多了 1024 字节的厂商头，去掉后才是标准 SQLCipher 文件 |
| 字段只有编号 | QQNT 的表和字段都是数字编号（如 `40001`、`40800`），消息内容是嵌套的 protobuf |
| 导入器漏掉很多类型 | 回复、旧版表情、商城表情、卡片、本地提示等，导入器直接跳过 |
| 群消息靠序号排序 | 群消息按序号 `40003` 显示，同一序号只显示一条；旧版很多提示没有序号 |
| 客户端运行时会改库 | QQ 在托盘里也在写库；只关窗口不够，必须从托盘退出 |
| 官方迁移看不到进度 | 导出到手机时，手机端合并阶段只显示「正在导入 x/y」，卡住和慢分不清 |

## 4. 第一段：补全 Windows 上的 QQNT

### 4.1 原则

- **只在副本上改。** 每次都先确认 QQ 已从托盘退出、主库没有 `-wal`/`-journal`，再复制一份实库，去掉厂商头，在副本上改。
- **先演练，再换库。** 演练用的是和实库相同的文件。演练通过后，再从退出时的实库重新复制一份来做正式修改，这样期间收到的新消息不会丢。
- **改完逐行核对。** 除了要改的行，所有表的每一行都要和修改前完全一样；同时要通过 `PRAGMA integrity_check`，群里也不能出现新的重复序号。
- **换库要保留权限和回滚源。** 新文件先放进同一目录，让它继承原文件的 ACL，核对一致后再用 `os.replace` 替换。换库前的实库原样保留，作为回滚源。
- **移开搜索索引。** 换库前把 `group_msg_fts.db`、`buddy_msg_fts.db`、`msg_fts.db` 移走，QQNT 下次启动会自己重建。
- **每一步都在客户端里验收。** 换库后由本人打开 QQ，按给出的时间点逐条查看样本。

### 4.2 步骤

1. **建立基线**：迁移前，把整套 `nt_qq` 目录复制一份并逐字节核对。
2. **逐条对账**：把旧版每条消息和 QQNT 里已有的消息按会话、时间、随机数配对，分成"已有""可写""暂不支持"几类，并记录原因。
3. **学写法**：每一类消息都去找 QQNT 自己写的样本，比如导入器写入的消息，或客户端原生收发的消息，从样本里学到字段和元素的结构。导入器写过的类型（如回复、经典表情），按规则重新生成一遍，再和导入器的结果逐字节比对。
4. **第一次补写**：写入能确认写法的文字和图片消息。
5. **按本人的决定删除**：先由本人确认哪些群和聊天不要，再按会话删除这些消息，然后执行 `VACUUM`。退出了的群，先生成一个本地网页给本人逐条查看，由本人选出要保留的群。
6. **补写剩下的类型**：本地提示、商城表情、卡片，以及要保留的退出群的消息。
7. **小修正**：有原图却被标成"已过期"的图片，恢复显示；回复和旧版经典表情，改用验证过的规则重写。

### 4.3 结果（主账号）

| 项目 | 结果 |
| --- | --- |
| 旧版私聊和群聊记录 | 524,471 条 |
| 导入器已导入 | 约 10.6 万条 |
| 本人决定不要的群和聊天 | 一个 40 万条的大群、另一个约 9 千条的群、6 个退出的群，以及 2 个私聊，全部删除 |
| 补写进 QQNT | 文字和图片、回复、表情、本地提示等，都已在客户端里验收 |
| 刻意不写 | 没有音频文件的语音、没有视频文件的视频、疑似重复的消息、找不到真实序号的群提示 |
| 数据库大小 | 删除大群并执行 `VACUUM` 后，从约 160 MB 降到约 35 MB |

### 4.4 图片和文件

消息行写进去以后，客户端还要能找到对应的文件。

**图片**
- QQNT 按 `nt_data/Pic/<月份>/Ori/<md5>.<扩展名>` 找原图，月份按消息时间在本地时区计算。旧版的图片在 `Image` 目录里，按旧文件名存放。
- 迁移时，按消息里记录的 md5 和大小，把旧图放到这个位置。在同一块盘上，优先用硬链接，不占额外空间。旧文件不动。
- 少数消息的原图字段（`45403`、`45812`）里还写着旧路径，要改成新路径。缩略图字段 `45814` 是另一回事，不要和原图字段混在一起统计。
- 找不到原图的图片，客户端会标成"已过期"（见 7.2）。原图放回去后，要改回可显示状态。

**文件**
- 历史文件消息里的路径字段 `45403`，可能还指向已经不存在的旧盘符（例如 `D:`）。我们按消息里的大小和 md5 找到原件，把路径改成 `::NTOSFull::<当前路径>` 的格式，客户端就能打开。
- 文件状态字段 `45550`：能打开的是 4，显示"文件已过期"的是 5。客户端点击过期文件时，会自己把 4 改成 5。有一条消息路径本来就对，只把 `45550` 从 5 改回 4 就能打开了。不要一律把 5 改成 4，先确认原件存在、路径正确。
- 同名、同大小不能证明是原件。我们遇到过同名同大小、但 md5 不同的文件，这种不能拿来替换。
- 在 Mac 上，私聊文件按 `nt_data/File/Ori/<45503 的值>/<文件名>` 放置，客户端就会显示为"已下载"。
- 群文件的结构和私聊不同，本地也基本没有原件，我们没有处理。

**规模**
主账号旧版图片目录约 57 GB、27 万多个文件。媒体检查用脚本做全量规则检查，再按会话、年份、类型分层抽样，最后只在客户端里打开少量样本，不逐个打开。

## 5. 第二段：迁到 Mac

### 5.1 做法

1. **先用官方的备份导入**：在 Windows 上导出备份，在 Mac 上导入。
2. **两边逐条对比**：分别取 Windows 和 Mac 的数据库快照，按"会话 + 时间 + 随机数"逐条配对，同时对比两边 `nt_data` 里的媒体文件（相对路径 + 大小）。
3. **补齐差异**：
   - 缺的消息：在 Mac 库的副本上，用 Mac 的密钥直接插入，不用重新加密。
   - 缺的媒体：按相同的相对路径复制到 Mac 的 `nt_data`，不覆盖已有文件。
4. **本人审核全部会话**：生成一个本地网页，左边是会话列表，右边是完整对话，右上角勾选删除，最后导出删除清单。按清单在 Mac 和 Windows 两边同时删除。

### 5.2 发现

- **官方备份能带走补写的内容。** 一个账号用备份从 Windows 导到 Mac 后，两边消息逐条一致，补写的灰条、商城表情、回复、退出群的消息都在。
- **官方备份不带图片原图。** 消息过去了，原图还在 Windows 上，要另外复制。语音和视频带过去了。
- **私聊只带最近约 200 个。** 另一个账号的私聊有近 300 个，备份导入后，最后一条消息在某个日期之前的私聊全部没过去，群都过去了。所以我们改为直接写库补齐。
- **在另一台设备上补写私聊，要同时补 `nt_uid_mapping_table`。** 私聊的会话槽 `40027` 是每台设备自己分配的。新分配的会话槽，如果没有在映射表里登记（会话槽、uid、QQ 号），客户端打开这个会话时就是一片空白。补上映射行，并把这张表的 `sqlite_sequence` 调到最大编号之后，就能正常显示。
- **退出的群，成员面板会显示上一个群的名单。** 这不是数据问题：这些群在 `group_info.db` 里根本没有成员数据，客户端就沿用了上一次加载的成员列表。

### 5.3 从手机再导回 Mac

手机上的记录导回 Mac 以后，Mac 的库从约 200 MB 涨到约 640 MB，多了约 36 万行。逐条和导回前的快照对比后，新增的行分成四类：

| 类别 | 行数 | 处理 |
| --- | ---: | --- |
| 已经删掉、又回来的会话（60 个） | 约 23.6 万 | 删除 |
| 确认的重复：同会话、同随机数、时间相差不超过 5 秒，发送人和内容也相同 | 约 1.6 万 | 删除手机导入的那一条 |
| 疑似重复：随机数相同、时间相近，但发送人或内容不同 | 约 1,300 | 不处理 |
| 保留的会话里真正新增的消息（电脑上从来没有，只在手机上有） | 约 11 万 | 保留 |

**发现**
- 删掉的会话之所以回来，是因为手机上还留着它们。要么在手机上也删掉，要么以后不再整机导回。
- **会话号为 0 的群消息不是一个独立的会话。** 其中很多行属于保留的群：它们的 `40021` 是群号，只是 `40030` 为 0。所以不能把"群 0"整个删掉，只能删和保留群里已有序号重复的那部分。私聊里也有会话号为 0 的提示。
- **重复图片：** 同一个月份目录里，同一 md5 同时存成 `.jpg`、`.png`、`.gif` 好几份，字节完全相同。主要来源是之前从 Windows 补复制媒体：Windows 上同一张图用了另一个扩展名。我们逐字节比较后，删除了数据库没有引用的那一份，共 12,770 个文件、4.9 GB。
- 删除会话后，要把搜索库（`buddy_msg_fts.db`、`group_msg_fts.db`、`msg_fts.db`）移开，让客户端重建。否则搜索里还能搜到已删除的会话。
- Mac 上没有 Python 的 `sqlcipher3` 时，可以用 Homebrew 的 `sqlcipher` 命令行完成删除，再用副本核对。

清理后，Mac 的库降到约 280 MB，账号目录从约 18 GB 降到 13 GB。客户端正常打开，没有重建库。

## 6. 第三段：导到手机

### 6.1 发现

- **卡在「正在加载」「正在准备聊天记录」，原因是 iPhone 上 QQ 的「本地网络」权限没开。** 「设置 → 隐私与安全性 → 本地网络 → QQ」打开之后，立刻就通了。在找到这个原因之前，我们排查过：
  - 电脑上的 Tailscale：电脑上的 QQ 实际监听的是 Wi-Fi 地址，不受影响。
  - 设备隔离的 Wi-Fi：有可能，但不是这次的原因。
  - 手机热点：运营商网络只有 IPv6 时，Mac 拿到的 `192.0.0.2` 是转换地址，QQ 在上面不开传数据的端口。把 APN 换成双栈后热点能拿到 IPv4，但仍然传不了，因为权限还没开。
- **导出到手机也带媒体文件。** 导出界面显示的预估大小不准，是按整个账号的文件索引（`files_in_chat.db`）算的。
- **导出到手机分两个阶段。** 先把数据传到手机，这时手机空间增长、电脑端显示导出成功；然后手机逐个会话合并进自己的数据库，界面只显示「正在导入 x/y」。
- **私聊只带最近 200 个，按最后一条消息的时间。** 我们在电脑上监控导出时生成的临时文件，确认一次导出正好打包了 200 个私聊和全部群；没带过去的，全是更旧的私聊。会话入口上的时间不影响这个挑选。
- **很大的会话会让人以为卡住了。** 一个约 10 万条消息、2 GB 媒体的私聊，手机端在它那里停了很久，序号一直不动，但等够时间就导完了。
- **手机导入是合并。** 同一个会话分几次导入，最后在手机上还是一个会话。

### 6.2 分批导出的办法

既然私聊一次最多 200 个，就让 QQ 每次只"看到"一批：

1. 从托盘退出电脑上的 QQ，完整备份实库。
2. 做一个临时库：只保留这一批会话的消息，其他会话的消息先拿掉；映射表、联系人、会话入口都保持不变。
3. 换上临时库，打开 QQ，「导出全部」到手机，等手机导完。
4. 退出 QQ，把临时库期间收到的新消息找出来，换回原库后合并回去，再逐字节核对原库。

用这个办法还能排查卡住的会话：哪一批卡住，就把那一批对半拆。我们按 3 批导完了一个账号的全部 331 个会话，并用拆分找到了那个"卡住"的大会话。

## 7. 踩过的坑

### 7.1 客户端

- **只关窗口不算退出。** QQ 在托盘里还会写库。替换数据库前，必须从托盘退出，并确认 `QQ.exe` 进程已经结束、主库没有 `-wal`。
- **客户端自己也会改库。** 浏览旧聊天时，QQ 会把下载失败的图片标成过期。我们演练时有 33 张，换库时已经变成 53 张。所以正式修改一定要基于退出时的实库，不能用演练前的旧副本。
- **退出了的群看不到。** 群消息写进去后，在会话列表和搜索里都找不到，补会话入口也没用。但记录仍在库里，官方备份和导出都会带上它们。
- **会话列表项尽量交给客户端处理。** 删除聊天记录时，入口可以留给本人在客户端里"从消息列表中移除"。
- **QQ 运行时复制的库，可能误报损坏。** 早期在 QQ 运行时复制的副本上，群消息表多次报 `SQLITE_CORRUPT`。完全退出 QQ 后重新复制，就没有这个问题。判断"库坏了"之前，先确认副本是在 QQ 退出后复制的。
- **旧版 `Msg3.0.db` 打不开，不等于损坏。** 它有 SQLite 文件头，但页面是加密的，普通 SQLite 读不了。
- **重签 QQ 副本这条路走不通。** 在 Mac 上，可以把 QQ 复制一份、重新签名后用调试器附加，但副本没有正式账号的权限，也读不到正式数据，不能用来取密钥。

### 7.2 数据库

- **SQLCipher 参数**：页大小 4096，`kdf_iter=4000`，`HMAC_SHA1`，`PBKDF2_HMAC_SHA512`。去掉前 1024 字节的厂商头后才能打开；换回去时，原样接上原来的厂商头。
- **群消息的序号**：群消息按 `(会话, 40003)` 排序和显示，同一序号只显示一条。旧版的序号在消息的 `Info` 里；`Info` 里没有时，可以去旧版的独立序号表 `group$<群号>$Seq$` 里，按"时间 + 随机数"找。只有找到唯一一条、而且这个序号在群里还没被占用时，才使用。**不要借用相邻消息的序号**，否则会把别的消息挤掉。
- **私聊的唯一键**是 `(会话槽 40027, 随机数 40002, 40005)`，补写时 `40005` 撞了就加 1。会话槽必须在 `nt_uid_mapping_table` 里有对应行。
- **消息 ID** 的高 32 位是写入时间，元素 ID 跟在消息 ID 后面顺序编号。同一条消息在不同设备上的消息 ID 一般相同，可以用来跨设备对比。
- **`40058`** 是消息当天在本地时区的零点；按消息当时的时区偏移计算，夏令时要算对。
- **原生回复、经典表情的写法**可以从导入器的输出里学到：回复是元素类型 7；旧版经典表情 ID 小于 255 时直接沿用，等于 255 时，真正的 ID 在子字段里。
- **本地提示**（"你撤回了一条消息"、通话失败、离线文件已接收等）可以写成 QQNT 本地的居中灰条：元素类型 8，子类型 17，内容是 `{"align":"center","items":[{"txt":"…","type":"nor"}]}`。需要注意，导入器自己对这类提示一条都不写。
- **商城表情**：旧版 type 12 里有表情包编号、表情 md5 和 key，可以对应到 QQNT 的商城表情元素（元素类型 11）。图片由客户端按编号从服务器取。
- **"已过期"的图片**：QQ 下载失败后，会在图片元素上加字段 `45507`，并把 `45509` 设为 1。原图放回本地后，还要删掉 `45507`、把 `45509` 改回 0，才会正常显示。
- **本机路径字段 `45812`**：每台设备都会写自己的路径。把一台设备的消息写到另一台时，要转换成目标设备的路径，或者干脆不写。

### 7.3 核对

- **粗配对会误判。** 只按"会话 + 随机数 + 时间"找到任意一条就算已有，可能把不同的消息算成同一条。必须一对一核对，并检查发送人。
- **"可以写"不等于"应该写"。** 撤回提示这类本地提示，导入器本来就不写；写不写由本人决定。我们写了，验收也正常。
- **不要相信界面上的数字。** 导出预估、文件夹大小都可能误导。要看实际打包了哪些会话、数据库里实际有哪些行。
- **先读完已有的核查记录。** 多人或多轮接手时，前一轮已经验证过的规则和结论，要在动手之前读完。
- **验收分层。** 消息在库里 → 原件和消息记录的大小、md5 一致 → 客户端实际访问的路径正确 → 在客户端里打开。前一层通过，不代表后一层也通过。
- **全量检查交给脚本，不交给人或 AI 逐条读。** 几十万条消息，用脚本按规则全量检查，再分层抽样，最后只在客户端里看少量样本。

## 8. 工具

### 8.1 用到的东西

| 工具 | 用途 |
| --- | --- |
| QQNT 官方客户端（Windows、Mac、iPhone） | 查看、验收、备份导入、导出到手机 |
| [sqlcipher3](https://pypi.org/project/sqlcipher3/) | 在 Python 里打开 SQLCipher 数据库 |
| [protocol_dbkey](https://github.com/QQBackup/protocol_dbkey) | 在 Mac 上取得本机 QQ 数据库的密钥 |
| Python 3.14、Windows 10、macOS | 运行环境 |

### 8.2 本仓库的脚本

[`tools/`](tools/README.md) 里收录了三段用到的脚本：
- **第一段**：旧版记录的逐条对账、按导入器样本核对转换规则、补写进库副本、恢复过期图片的显示。
- **第二段**：两台设备的逐条对比、补写缺少的消息、补映射行、按清单删除会话、会话审核网页、媒体文件对比。
- **第三段**：分批导出到手机。

脚本里不包含账号、路径和密钥。所有输入都用命令行参数传入，密钥只通过环境变量传入。取得密钥和解密旧版 `Msg3.0.db` 的方法不在本仓库里。

## 9. 说明

- 只在自己的账号和自己的设备上使用这些方法。
- 取得密钥和解密，只是为了处理自己的数据。不要把密钥、数据库或聊天内容上传或分享给任何人。
- 直接修改 QQ 的数据库有风险：客户端可能报错，数据可能损坏，也可能和服务器状态不一致。动手之前，一定要有一份完整的原始备份。
- QQ 的版本和数据结构会变化。本文基于 Windows 版 QQNT 9.9.36.53644、Mac 版 QQ 7.0.2，时间是 2026 年 11 月。
